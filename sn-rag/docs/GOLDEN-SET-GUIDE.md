# Writing the Golden Set

The golden set is the evaluation dataset for retrieval: **questions paired with the
documents that should answer them**. It is the only thing that turns "does search
work?" from an opinion into a measurement.

Everything built on top of retrieval — the agent loop, the MCP tools, the claimed
token savings — assumes retrieval surfaces the right document. This file is what
tests that assumption.

---

## 1. What a case looks like

```yaml
- id: glideajax-async-callback
  question: "why does my GlideAjax callback fire before the value is set"
  profile: servicenow
  expected_rel_paths:
    - ServiceNowOfficialDocs/api-reference/c_GlideAjaxAPI.md
  notes: "Real question from debugging a client script in Feb."
```

| field | meaning |
|---|---|
| `id` | unique slug |
| `question` | phrased the way you would actually type it |
| `profile` | `general` (everything) / `servicenow` (official docs only) / `personal` (your own notes only) |
| `expected_rel_paths` | files that *should* be retrieved. **Any one** counts as a hit — list genuine alternatives, not every loosely related file |
| `expect_no_answer` | `true` when the corpus genuinely cannot answer. See §5 |
| `notes` | optional; why the case matters |

---

## 2. The rule that makes or breaks the whole exercise

> **Write the question before you look at the document.**

If you write a question while reading the document that answers it, the question
inherits that document's vocabulary. Retrieval then matches on shared vocabulary,
recall comes out near-perfect, and you have measured nothing except that the same
words appear twice.

Real questions are phrased in *your* words, which frequently do not appear in the
document at all. You ask "why is my business rule running twice"; the doc is titled
"Order of execution for server-side scripts". Closing that gap is the entire job of
semantic retrieval — and a reverse-engineered question hides whether it works.

The same applies to picking expected paths. **Never choose them from the semantic
search's own results.** That is circular: grading retrieval against what retrieval
already found. `scripts/golden.py find` deliberately uses filename matching and
ripgrep only, so it cannot contaminate the set this way.

---

## 3. Where to get real questions

Ranked by value:

1. **Your own history.** Claude Code transcripts, `raw/sessions/`, `chats/`, past
   tickets, Slack/Teams searches. These are real questions with known answers and
   are worth more than anything invented.
2. **Recent work.** The last handful of things you had to look up. Write them down
   before the memory of *how you phrased it* fades.
3. **Recurring questions.** Things you look up repeatedly, or that colleagues ask
   you. High-value because the system will face them often.
4. **Things that annoyed you.** Questions the current `INDEX.md` + grep workflow
   handled badly. These are the ones the project exists to fix.

Avoid: questions generated by reading documents, and questions phrased in
documentation language rather than working language.

---

## 4. Coverage to aim for

At least **30 real cases**, at least **3 per profile**, and a handful of negatives.

| category | why it matters | example shape |
|---|---|---|
| Exact API symbols | tests the lexical/exact path | "GlideRecord addQuery vs addEncodedQuery" |
| "How do I" tasks | procedural docs, different retrieval shape | "how do I make a catalog item visible to one group" |
| Conceptual, no single page | tests multi-document assembly | "how do ACLs and query business rules interact" |
| Release-specific | tests facet filtering | "what changed in Zurich for Flow Designer" |
| Personal-notes-only | proves your notes aren't buried under 51k official docs | "my notes on the capacity planner rollout" |
| Official vs personal disagree | tests source attribution | anything where your notes correct the docs |
| **Negatives** | proves the system says "I don't know" | see §5 |

Ambiguous or badly-phrased questions are *good* cases. Real questions are often
vague; a system that only handles well-formed queries is not useful.

---

## 5. Negative cases — do not skip these

Questions the corpus genuinely **cannot** answer:

```bash
python3 scripts/golden.py add \
  --id negative-pricing \
  --question "what does a ServiceNow ITOM licence cost per node" \
  --profile servicenow \
  --expect-none
```

The build spec's adversarial smoke test #3 states that **any fabricated answer is a
build failure**. Without negative cases there is nothing to detect fabrication with.
A system that confidently invents an answer is far worse than one that returns
nothing, and this is the only way to catch it.

Aim for 3–5.

## 6. Workflow

```bash
cd sn-rag
export CORPUS_PATH=/path/to/obsidian-servicenow-docs

# find the doc you already believe answers your question
python3 scripts/golden.py find "GlideAjax"
python3 scripts/golden.py find "order of execution"

# record the case
python3 scripts/golden.py add \
  --id business-rule-runs-twice \
  --question "why does my business rule run twice on insert" \
  --profile servicenow \
  --expect "ServiceNowOfficialDocs/now-platform/..." \
  --notes "Hit this debugging the intake integration"

# a question nothing answers
python3 scripts/golden.py add --id neg-licence-cost \
  --question "what does an ITOM licence cost" --expect-none

# progress and gaps
python3 scripts/golden.py check
```

`add` refuses nonexistent paths and duplicate ids, so a typo fails immediately
rather than silently scoring zero at eval time.

---

## 7. When it is ready

```bash
python3 scripts/golden.py check      # no errors, no coverage gaps
python3 eval/run_eval.py             # real numbers
```

`run_eval.py` reports recall@5, recall@10, MRR and p50/p95 latency for
`dense | sparse | hybrid | hybrid+rerank`, per profile, and enforces the Phase 4
gate: **hybrid+rerank recall@10 >= 0.85**.

That run also settles DECISION-2 (`bge-base` 768d vs `bge-small` 384d), which is
currently chosen on indexing throughput alone with no quality evidence. Doing this
before the full 525k-chunk index avoids embedding the corpus twice.

If the gate fails, that is a useful result, not a setback — it means tuning
retrieval now rather than discovering the problem after an agent has been built on
top of it.

---

## 8. Honest expectations

- Recall will **not** be 1.0. Anything near it means the questions are
  reverse-engineered.
- Some cases will fail for boring reasons — the expected document is not indexed
  yet (the index is partial), or the question is genuinely ambiguous. `run_eval.py`
  prints which case ids missed so you can tell real failures from artefacts.
- 30 cases is a floor, not a target. 50–100 makes tuning decisions far more
  trustworthy, but 30 is enough to gate on.

## Provenance — added 2026-08-04

Every case now carries a required `provenance` field:

```yaml
- id: my-question
  provenance: real | constructed | negative
```

| value | meaning | counts toward the Phase 4 gate? |
|---|---|---|
| `real` | you asked it before you knew the answer | **yes** |
| `constructed` | written while reading the document it should find | no |
| `negative` | the corpus genuinely cannot answer it | no (Phase 5 signal) |

### Why the split exists

A question written by reading its own answer inherits that document's vocabulary.
Retrieval then finds it easily, recall comes out high, and the number measures the
author's memory rather than the system. That is not a small distortion: the 26
constructed cases currently score **1.000 on the `personal` profile** — a perfect
score, which is what circularity looks like from the outside.

`eval/run_eval.py` therefore scores the gate on `real` cases only. With fewer than
20 it exits **2 = INCONCLUSIVE** — neither pass nor fail — rather than reporting a
blended number that would look earned.

### Where real cases come from

1. **Mined from transcripts.** `python3 scripts/mine_questions.py` scans
   `~/.claude/projects/**/*.jsonl` for questions you actually typed. This source is
   now exhausted: 247 user messages across 18 transcripts yielded 5 domain
   questions, all already in the set. Your ServiceNow lookups went through
   Obsidian, which Claude Code never saw.
2. **Written from memory** — the remaining path. Recall a question you hit last
   month, write it in the words you used *then*, and only afterwards look for the
   document. If you find yourself opening a file first and then phrasing a
   question around it, that case is `constructed`; label it honestly.

```bash
python3 scripts/golden.py find "your question here"      # filename + ripgrep only
python3 scripts/golden.py add --id ... --question ... --expect ... --provenance real
python3 scripts/golden.py check
```

`golden.py find` deliberately never uses vector search: picking expected paths from
the system's own output would make the eval grade retrieval against its own opinion.
